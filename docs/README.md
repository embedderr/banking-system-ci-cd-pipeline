# Project Documentation

This folder contains the full SDLC documentation for the Banking System project,
following a V-Model approach. Every requirement, design decision, and test case
is version-controlled alongside the source code, so history and rationale are
never lost.

---

## The V-Model, Explained for This Project

The "V" has two arms: the **left side** goes from broad → detailed (defining
what to build), and the **right side** goes from detailed → broad (testing
what you built) — each right-side stage validates against its matching
left-side stage.

```
Business Requirements (BRS)  ─────────────────────────  User Acceptance Testing (UAT)
        │                                                          │
Software Requirements (SRS)  ───────────────────────  System / Functional Testing
        │                                                          │
Architecture + High-Level Design (HLD)  ──────────────  Integration Testing
        │                                                          │
Low-Level Design (LLD)       ─────────────────────────  Unit Testing
        │                                                          │
         └──────────────────  Coding  ──────────────────┘
```

**Why this order matters**: each left-side document is written *before* the
one below it, and each right-side test is written *against* its paired
left-side document — ideally *before* the corresponding code even exists
(test-first mindset). For this conversion project, test cases are written
right after the matching design doc, before touching code for that module.

## A Note on Architecture

In larger or multi-service systems, "Software Architecture" is often a
separate document from HLD, owned by a dedicated architect role. For a
**single-binary, single-process application** like this Banking System
(no microservices, no distributed components, no database), industry
practice is to **fold architecture into HLD** as its own clearly-labeled
section. This is not a shortcut — it's the correct scope for a project this
size. `design/HLD.md` therefore begins with an **"Architecture Overview"**
section covering:
- Overall architecture style (modular monolith, single process)
- Layering: UI screens → business logic (account/queue modules) →
  platform abstraction → OS
- Key architectural decisions and their rationale (e.g., fixed-size buffers
  over dynamic strings, struct+function modules over C++-style classes)

before drilling into per-module HLD detail.

## Mapping This to Our Project, Stage by Stage

| Stage | What It Means Here | Format |
|---|---|---|
| **BRS** (Business Requirements) | Why this system exists, who uses it (customer, admin), what business problem it solves — no technical detail | Excel, Sheet 1 |
| **SRS** (Software Requirements) | Functional requirements broken down from BRS — e.g., "System shall allow account holder to withdraw cash if balance sufficient" — each with a unique ID | Excel, Sheet 2 (same workbook) |
| **Architecture + HLD** | Overall architecture, module breakdown, how modules talk to each other, data flow | `design/HLD.md` |
| **LLD** (Low-Level Design) | Per-module detail: struct definitions, function signatures, parameters, return values, error handling — written *before* the `.c` files | `design/LLD.md` |
| **Coding** | The actual `.c`/`.h` files | `../src/`, `../include/` |
| **Unit Testing** | Test cases per function — input, expected output, edge cases | `testing/unit_test_cases.xlsx` |
| **Functional / System Testing** | End-to-end scenarios across modules | `testing/functional_test_cases.xlsx` |
| **UAT** | Sanity-check against BRS — does the finished system satisfy the original business need? | `testing/uat_checklist.xlsx` |
| **Requirement Traceability Matrix (RTM)** | Maps every BRS → SRS → HLD module → LLD function → Unit Test → Functional Test, so nothing is unimplemented or untested | `traceability/RTM.xlsx` |

## Release Notes (Not Part of the V-Model)

`CHANGELOG.md` (repo root) is auto-generated by git-cliff from conventional
commits — a technical, commit-level record of every change.

**Release Notes** are a separate, human-written artifact: a plain-language
summary of what a release means for the people using it (e.g., "You can now
change your ATM PIN from the self-service menu" instead of "fix: updated
pin change logic"). This is a release-management concern, not a V-model
stage — it lives alongside the other docs for convenience and discoverability.

```
docs/release-notes/
├── v7.0.0.md
├── v8.0.0.md
```

## Versioning Convention

Every document uses a stable ID scheme so it can be referenced from the RTM:

- Business Requirements: `BRS-001`, `BRS-002`, ...
- Software Requirements: `SRS-001`, `SRS-002`, ...
- Unit Test Cases: `UT-001`, `UT-002`, ...
- Functional Test Cases: `FT-001`, `FT-002`, ...

Each document change should be committed with a clear message describing
what changed and why (e.g., `docs: add SRS-014 for ATM PIN change flow`).
